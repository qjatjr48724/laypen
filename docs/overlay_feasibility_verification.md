# 오버레이 구현 가능성 검증 결과

- 문서 버전: 0.1
- 검증일: 2026-10-16
- 검증 방식: 공개 API·Apple 개발자 포럼·App Store 유사 앱·관련 문서 조사
- 대상: 제안서 P0 — 다른 앱 위 투명 필기 레이어
- 상태: **핵심 요구사항은 공개 API로 충족 불가**

---

## 1. 검증 대상 정의

제안서의 핵심 요구사항:

> Safari, 영상 앱 등 **다른 앱을 사용하는 중**에, 그 화면 **위에 투명한 인터랙티브 필기 레이어**를 표시하고 Apple Pencil로 직접 필기한다.

충족 조건:

| 조건 | 설명 |
|---|---|
| A | 다른 앱이 포그라운드인 상태에서도 필기 UI가 계속 표시됨 |
| B | 배경(아래 앱 화면)이 투명하게 보임 |
| C | 필기 터치(Pencil)가 오버레이로 정상 전달됨 |
| D | 아래 앱의 스크롤·탭과 충돌을 제어할 수 있음 |
| E | App Store용 **공개 API**만 사용 |

---

## 2. 결론 (요약)

| 방식 | 핵심 요구 충족 | 비고 |
|---|---|---|
| 앱 내 `UIWindow` / 투명 캔버스 | ❌ | 자기 앱 씬 안에서만 동작 |
| `UIWindow.Level` 조작 | ❌ | 같은 앱의 창 간 z-order만 변경 |
| Accessibility / AssistiveTouch 유사 오버레이 | ❌ | 시스템 전용, 서드파티 불가 |
| Screen Time Shield | ❌ | 차단용 고정 UI, 필기 불가 |
| ReplayKit / ScreenCaptureKit | ❌ | 화면 **캡처**용, 화면에 그리는 오버레이 아님 |
| Slide Over / Split View | △ | 창으로 나란히/위에 표시. **아래 앱에 직접 투명 필기 ≠** |
| Picture in Picture (커스텀 콘텐츠) | △ | 다른 앱 **위 떠 있는 창** 안에 필기 가능. 전체 화면 투명 오버레이 ≠ |

**최종:** 원래 정의한 “다른 앱 화면 위 전체(또는 넓은) 투명 필기 레이어”는 **iPadOS 공개 API로 구현할 수 없다.**  
Apple이 멀티태스킹·보안상 의도적으로 막는 영역이며, Android의 `SYSTEM_ALERT_WINDOW`에 해당하는 권한이 없다.

---

## 3. 방식별 상세

### 3.1 일반 앱 창 (`UIWindow`)

- `UIWindow`는 **해당 앱의 UI 씬**을 위한 창이다.
- `windowLevel`을 올려도 **다른 앱 위**에 표시되지 않는다.
- Apple Developer Forums: floating widget on top of other apps → **“For iOS, the answer is simply No.”**

### 3.2 Slide Over / Split View / Stage Manager

- 사용자가 선택한 **별도 앱 창**으로 표시된다.
- 창 안에서 필기하는 것은 가능하나, 아래 앱 픽셀 위에 투명하게 그리는 경험이 아니다.
- 제안서 9.1과 동일: **핵심 요구사항 충족으로 간주하지 않음.**

### 3.3 Screen Time / Shield

- 특정 앱·웹을 막을 때 시스템이 보여주는 차단 오버레이다.
- 커스터마이즈는 제목·버튼 수준이며, 자유 필기 캔버스가 아니다.

### 3.4 ReplayKit / Broadcast / ScreenCaptureKit

- 화면을 **녹화·전송**하는 API다.
- 다른 앱 위에 인터랙티브 그리기 레이어를 올리는 용도가 아니다.

### 3.5 Picture in Picture (가장 가까운 대안)

App Store에 PiP로 “다른 앱 위에 떠 있는” 콘텐츠를 보여주는 앱이 있다 (예: Floathing, Pip Up).

가능한 것:

- 작은 **PiP 창**을 다른 앱 위에 유지
- 그 창 **안**에 메모·드로잉 보드 표시
- iOS 15+ `AVPictureInPictureController.ContentSource` + `AVSampleBufferDisplayLayer`로 커스텀 화면을 PiP에 넣는 패턴이 커뮤니티에 존재

불가능한 것 / 차이:

- Safari·영상 화면 **전체에 투명하게** 덧그리는 경험 아님
- 필기는 PiP **창 영역 안**으로 제한
- 아래 앱과 터치가 동시에 “한 레이어”처럼 동작하지 않음
- 시스템 PiP UI·크기·정책 제약
- 리뷰 정책·`UIBackgroundModes`·미디어 성격에 따라 거절 위험 가능 → **별도 검증 필요**

macOS용 “Screen Annotations” 등은 **진짜 화면 오버레이**를 하지만, iPad 쪽은 화이트보드로 분리된 사례가 있어 **Mac ≠ iPad** 제약을 보여 준다.

## 5. 대응 권고 (제안서 9.3 기준)

1. **원래 오버레이:** 공개 API 경로 없음 → 그대로는 본개발 착수 불가.
2. **즉시 포기하지 않음:** 아래 대안을 사용자와 비교·선택.
3. **대안 후보 (우선 논의):**

| 대안 | 장점 | 단점 | 원래 요구와의 차이 |
|---|---|---|---|
| A. PiP 플로팅 필기 창 | 다른 앱 위에 상시 표시 가능에 가장 가까움 | 전체 화면 투명 필기 불가, 시스템 PiP 제약 | 큼 |
| B. Slide Over 전용 필기 앱 | 구현·심사 리스크 낮음 | 창 안 필기만 | 큼 |
| C. 자앱 풀스크린 + (선택) 화면 공유/미러 참고 | Pencil UX 완성도 높음 | 다른 앱과 동시 사용 불가 | 매우 큼 |
| D. 요구사항 변경 후 개발 보류 | 잘못된 기대 방지 | 제품 방향 재정의 필요 | — |

4. 대안을 채택하려면 **원래 기능과의 차이를 명시하고 사용자 승인** 후 범위를 바꾼다.

---

## 6. 실제 기기 검증에 대해

코드 PoC 없이도, Apple의 앱 샌드박스·멀티태스킹 모델상 **조건 A+B+C를 동시에 만족하는 공개 API는 존재하지 않는다**는 점이 업계·공식 포럼에서 장기간 동일한 결론이다.

남은 실기기 검증이 의미 있는 경우:

- **PiP 대안**을 채택할 때만: Pencil 입력, 투명도, 백그라운드 유지, App Store 정책을 **실기기 PoC**로 확인
- 원래 오버레이를 다시 시도하는 PoC는 **기대 효과가 없음** (실패가 이미 플랫폼 제약으로 확정)

## 7. 채택 결정 (2026-10-16 / 사용자 승인)

**결정:** 시스템 전역 오버레이는 포기하고, **스크린샷 + Share Extension** 마크업으로 1차 제품을 진행한다.

| 항목 | 내용 |
|---|---|
| 채택 | `스크린샷 → 썸네일 → 공유 → Laypen` 필기 |
| 보조 진입 | 메인 앱에서 앨범/최근 스크린샷 선택 |
| 비채택 | 백그라운드 스크린샷 자동 감지, 제어 센터에서 타인 화면 캡처, PiP를 1차 본선으로 채택 |
| ON/OFF | OFF여도 필기 유지, 입력만 차단 |
| 이후 | OS가 오버레이 공개 API를 열면 `BackgroundSource` 교체로 재검토 |

원래 요구와의 차이: 다른 앱과 **동시**에 투명 필기하는 경험이 아니라, **정지된 스크린샷 이미지 위**에 필기한다. 절차를 줄이기 위해 Share Extension을 기본 진입으로 둔다.

상세 MVP 범위는 [mvp_scope.md](mvp_scope.md), 제안서 반영본은 [ipad_overlay_handwriting_app_proposal.md](ipad_overlay_handwriting_app_proposal.md)를 본다.

## 8. (참고) 검토만 하고 채택하지 않은 경로

1. PiP 플로팅 필기 창 — 1차 비채택 (경험·정책 리스크, 원래 요구와 차이 큼)
2. Slide Over 전용 — Share 마크업과 병행 가능하나 기본 진입은 아님
3. 개발 보류 — 채택하지 않음; 대안 범위로 본개발 진행
